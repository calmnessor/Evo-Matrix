## 一句话总结

RTC 让 VLA 的推理和动作执行**并行进行**：在动作块执行的同时开始推理下一块，用冻结论证+修复未执行部分的方式消除推理延迟对控制频率的影响，无需重新训练任何模型。

## 核心动机

### Action Chunking 的"空闲时间"困境

所有现代 VLA 都在用 Action Chunking——一次推理预测 H 步动作，执行 H 步后再推理下一次。这存在一个根本问题：

```
时间线:
  ████████████ 执行 H 步动作 (比如 50 步 = 1 秒)
                ░░░░ 推理 (VLM 前向 + Flow Matching, ~200ms)
                      ████████████ 执行下一个 H 步
                                    ░░░░ 推理

问题: 推理的 200ms 内，机器人是"发呆"的!
      → 机器人停住 → 动作不连贯 → 动态任务会出问题
      → 人对机器人行为的体感变差
```

### 为什么不直接减小 H？

H 太小 → 短视 → 动作不连贯 → 任务性能下降。
H 太大 → 推理间隔长 → 发呆时间长 → 对动态变化反应慢。

Action Chunking 的 H 是一个 trade-off 参数。RTC 的目标是**打破这个 trade-off**：保持大 H 的优势（长视），同时消除发呆时间。

## 方法

### 核心思想：异步推理 + 原地修复

```
RTC 的时间线:
  执行开始 (H=50 步，K=10 步已推理完成)
    ↓
  ████████████████████████████████████████████████ 执行 50 步
    ↓ K 步后                              ↓ H-K 步后
    开始推理下一块 (后台)                   推理完成，准备切换
  ██████░░░░░░░░░░░░██████████████████░░░░░░░░░░░░████
    K 步执行  后台推理   继续执行剩余  后台推理下一个...

关键: 机器人在执行的同时，后台在推理!
      → 没有发呆时间
      → 控制频率始终 50Hz
```

### 具体算法

RTC 依赖两个技术：**Action Freezing** 和 **Inpainting**。

#### 步骤 1：Action Freezing（冻结论证）

推理有延迟 D（秒），在 D 期间内必须继续执行动作（不能等）。问题在于：我们还没推理完，不知道 "正确的" 动作是什么。

**解决**：在推理完成前，继续执行**上一块的后 K 步**（K = D × 控制频率，保证机器人不停）。

```
上一块的输出: [a₀, a₁, ..., a₄₉] (50 步)
当前推理中:   执行 a₄₀, a₄₁, a₄₂ (已经 "过期" 的动作)
             同时后台在推理新块
```

#### 步骤 2：Inpainting（动作修复）

新的推理块预测 H 步动作。但前 K 步已经在执行中了——它们的值已经被"冻住"。剩下的 H-K 步需要被修复：

```
需要: [冻结区 (K 步) | 修复区 (H-K 步)]

方法: 用伪逆引导扩散/流匹配 (ΠGDM — Pseudo-Inverse Guidance for Diffusion Models)

数学直觉:
  - 把动作块想象成一条轨迹
  - 前 K 步 = 轨迹的起点约束（已知，已执行）
  - 后 H-K 步 = 在约束下重新生成（保证与冻结部分平滑连接）
  - 等价于: 在扩散去噪的每一步，把前 K 步"投影"回冻结值
```

#### 投影公式（ΠGDM 核心）

```python
# 伪代码：ΠGDM 在 Flow Matching 中的应用
def rt_chunk_predict(model, context, frozen_actions, K):
    """
    model: Flow Matching 动作专家
    context: VLM 输出的特征
    frozen_actions: 前 K 步动作（已经/正在执行的）
    K: 冻结步数
    """
    # 从噪声开始
    x = torch.randn(H, act_dim)  # H 步动作块

    # Flow Matching ODE 积分 (e.g., Euler, 5-10 步)
    for t in linspace(1, 0, N_steps):
        # 标准 Flow Matching 向量场预测
        v = model(x, t, context)

        # Euler 步
        x = x + v * dt

        # ΠGDM 投影：把前 K 步"拉回"到冻结值
        # P = 选择矩阵 [I_K | 0] → 取出前 K 步
        # x_frozen = frozen_actions
        # 用伪逆将前 K 步投影到目标值
        x[:K] = frozen_actions  # 硬约束：前 K 步 = 冻结值

    return x  # [H, act_dim] — 前 K 步 = 冻结，后 H-K 步 = 修复的
```

#### 为什么用伪逆投影而不是简单的替换？

简单替换 = 冻结区和修复区之间可能不连续 → 动作跳变 → 机器人抖动。

伪逆投影 = 在扩散/流匹配的每一步都满足约束 → 冻结区和修复区之间**自然平滑过渡** → 机器人不抖动。

### 为什么无需重新训练？

RTC 是对推理过程的修改——它在**推理时**操作动作块的生成方式，不改变模型参数、架构、训练数据。

任何用扩散或流匹配做 Action Chunking 的 VLA 都可以直接接上 RTC。这是它最大的实用价值。

### 后续改进：训练时 RTC

问题：ΠGDM 的投影步骤在每个 ODE 步都要执行，有额外的计算开销（~27ms）。

训练时的替代方案：在训练中模拟推理延迟，让模型**原生学会**修复被冻结的部分。

```
训练数据构造:
  动作块 [a₀, a₁, ..., a₄₉] (50 步)
    → 随机选 K (模拟推理延迟)
    → 前 K 步: 真实动作 (作为输入条件)
    → 后 H-K 步: 加噪声 (作为预测目标)
    → 修改 Flow Matching 时间步:
       前 K 步: t=1 (已 "干净"，无需去噪)
       后 H-K 步: t ∈ [0,1] (需要去噪)
    → Loss 只在后 H-K 步上计算

效果: 
  - 推理时零额外开销 (无 ΠGDM 投影)
  - 108ms vs 135ms 延迟
  - 性能在高速率下更好
```

## 关键结果

### 动态 Kinetix 基准 (12 任务)

| 推理延迟 | No RTC | RTC (推理时) | RTC (训练时) |
|---------|--------|-------------|-------------|
| 100ms | 基线 | 持平 | 持平 |
| 150ms | -12% | -3% | -2% |
| 200ms | -25% | -8% | -5% |

**关键**: 延迟越高，RTC 的优势越明显。

### 真实世界双臂任务

| 任务 | 无 RTC | 有 RTC |
|------|--------|--------|
| 划火柴 | 困难 | 成功 |
| 插以太网线 | 困难 | 成功 |
| 叠衣服 | 抖动 | 平滑 |
| 装箱 | 可接受 | 更流畅 |

## 贡献与影响

1. **打破延迟-精度 trade-off**：推理不再等于发呆，可以边推理边执行
2. **零训练成本**：任何扩散/流匹配 VLA 可即插即用
3. **训练时替代方案**：训练时 RTC 用 3 行代码实现，零推理开销
4. **工业级实时性**：让 VLA 的控制频率真正达到 50Hz 不间断

## 局限

- 推理时 RTC 的 ΠGDM 投影有额外计算（~27ms），可能抵消部分收益
- 对非扩散/流匹配的动作生成方式（如自回归离散 token）不适用
- 如果推理延迟 > 动作块长度，RTC 失效（H 步不够 "缓冲"）
- K 的选择需要与实际推理延迟匹配
